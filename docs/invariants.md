# Runtime invariants — long form

The full statement of every contract summarised in [AGENTS.md](../AGENTS.md), with the
mechanics and the rationale that stops each one being re-broken. AGENTS.md is the
per-turn contract sheet (kept under 32 KB so both hosts load it cheaply); this file is
the reference it points at. Edit the two together: a contract change lands here in
full and in AGENTS.md as a one-line statement plus pointer. Release archaeology still
lives in [CHANGELOG.md](../CHANGELOG.md) and [ROADMAP-TO-GA.md § Post-GA audit log](../ROADMAP-TO-GA.md#post-ga-audit-log).

## 1. Native-v2 safety contract (the Version headline)

- **Version**: 2.4.1 (kimi-code, subprocess transport, **native agent-core-v2**). **The native-v2 safety contract — the current headline, do not regress:** every executed tool call in a plugin-managed session passes the managed PreToolUse hook, and the engine's sole chain-breaking final allow (the plan-file guard, `features/plan/planService.ts`, active plan mode only) is NEVER armed. That is a construction, not an upstream ordering promise, and it rests on four plugin-owned closures that must all stay in place: (1) `runtime/native-v2-preflight.ts` refuses the default-plan-mode setting under EVERY spelling upstream's loader normalizes to the `defaultPlanMode` domain (`default_plan_mode`, `defaultPlanMode`, mixed — it mirrors upstream's `snakeToCamel` verbatim, pinned by the tag scan; the `[experimental]` table keeps raw keys and is NOT normalized) unless absent or literal `false` — parsed from the SAME `<KIMI_CODE_HOME>/config.toml` the child reads once inside `sessions.create()`, before spawn and again at the spawn boundary, with `KIMI_CODE_HOME` resolved against the child's cwd on every entry path incl. the Stop hook (`CLI_V2_PLAN_MODE_CONFIGURED`, remedy is the config key, NEVER `/kimi:setup`); (2) the hook denies `EnterPlanMode`/`ExitPlanMode` for every label (`runtime/hooks/approval-policy.ts`); (3) resume accepts only proven `native-v2` plugin lineage (`KIMI_SESSION_LINEAGE_UNKNOWN` for unknown rows, `KIMI_SESSION_ENGINE_MISMATCH` for v1) after a raw scan of every agent `wire.jsonl` for `plan_mode.*`/`plan.*` records (`KIMI_SESSION_PLAN_TAINTED`) — `restore()` folds only that journal, nothing else can restore plan state; (4) v2-only experimental features (`tower`, `subagent_fork`, from `[experimental]` config or per-flag env) and the master `KIMI_CODE_EXPERIMENTAL_FLAG` refuse before spawn. Certification is per EXACT version and per operation (`NATIVE_V2_CERTIFIED` in `runtime/kimi-engine.ts`; `KIMI_TESTED_MINORS` is the legacy-v1 table and never gains 0.42); a new kimi-code version is appended only after `tests/audit/v2-tag-scan.test.ts` passes against its source tree, the plan-mode-ON live control still shows the bypass (proving the refusal is load-bearing), and the per-operation smoke is green. A native-v2 plan REQUIRES the `system.version` marker as the first stream-json line and requires it to equal the probed version; a legacy plan still refuses it (`CLI_ENGINE_PROVENANCE_MISMATCH`, teardown before any record is delivered). `Bash.cwd` is validated against the trusted root before the command string (`runtime/rescue-approval.ts`) — the hook payload's top-level `cwd` is the process cwd, not the Bash cwd. Basis and residuals: `docs/native-v2-certification-provenance.md` §2. **Hook-pin durability contract (unchanged):** the canonical hook command must never embed a version-stamped Node token. `preferStableNodePath` prefers `process.argv0` over `process.execPath` ONLY when it is absolute AND `realpath`-identical; `verifyHookInstalled` runs `access(nodeBin, X_OK)` fail-closed; `nodeBin` is parsed back from the built command (`parseHookShellCommand`), never re-resolved. That check covers only "config and expected command still byte-equal, yet the embedded node token fails X_OK" (`refusal_kind:"node-bin-not-executable"`, the one refusal whose remedy is NOT /kimi:setup). Re-pin-recoverable refusals carry `drift`/`hookRefusalDetails`; agents re-pin through `${CLAUDE_PLUGIN_ROOT}/scripts/companion.sh setup` and retry ONCE only when `retryable_after_setup` AND setup exits 0 (`hookRefusalRetryProtocol`, single source in `hooks/install.ts`). Startup-failure wraps thread `availability`/`cause_code`/`cause_message` into `details`; `auth.login_required` classifies to `*_KIMI_AUTH_UNAVAILABLE` with a `kimi login` remedy. **In-verifier auto-repin is REJECTED — do not re-propose.** **Background-worker test discipline:** detached-worker hook-enforcement tests MUST run the companion CLI as a real node subprocess through a symlink with NO `KIMI_PLUGIN_CC_NODE_BIN` override and NO `KIMI_PLUGIN_CC_SKIP_HOOK_CHECK` (`tests/runtime/background-hook-enforcement.test.ts`). **Smoke-home representativeness:** a real-binary smoke case MUST assert its own precondition when the behaviour under test depends on host state; do NOT write a "plan-file write is denied under plan mode" smoke — under this construction that path is never armed and a green result would be exactly the vacuous-precondition failure. **Full per-version release + compat history → [CHANGELOG.md](../CHANGELOG.md) and [ROADMAP-TO-GA.md § Post-GA audit log](../ROADMAP-TO-GA.md#post-ga-audit-log).**

### Hook-escape monitor (detection evidence)

**Hook-escape monitor** (§1): the cli-client replays the pure hook policy on every streamed `tool_calls` entry; a call the policy denies whose tool result is not the hook's denial (byte-exact, or with upstream's repeat-breaker `<system-reminder>` decoration / handoff text) is recorded as `mismatch`, and a denied call still without a result at settlement as `unresolved`. Findings are **detection evidence, never a failure**: logged (`hook_escape`), persisted on the job row (`hook_escapes`, JSON), exposed by `status`/`result --json`, printed as a stderr `safety hook notice`, and carried in timeout details; the run continues, the job's outcome is unchanged, and the review gate stays fail-open and only annotates. The stream has no outcome field, so a mismatch is equally an upstream pre-hook rejection (unknown tool, disabled tool, invalid args, sensitive path, per-tool resolve errors), a coexisting hook or permission policy blocking first, or hook drift — failing the job needs positive execution evidence this stream does not provide. Streamed calls under read-only labels are covered (swarm subagents are in-process, not streamed); write labels only for the pure denials (plan/goal tools).

The pure policy is shared with the live hook without changing any decision (`decideHookOutcomePure`; the async `decideHookOutcome` is pure-then-evaluator). For each assistant tool call, JSON arguments are parsed; malformed JSON and non-plain objects become `{}`, matching upstream hook input normalization. Pure denials are held by tool-call ID with the exact reason; filesystem-evaluator markers are ignored, never re-evaluated after execution. A tool record clears the pending denial when `carriesDenial` holds: byte-equal content, the reason followed only by upstream repeat-breaker `\n\n<system-reminder>…</system-reminder>` blocks, or upstream's fixed handoff-veto text. Anything else is `kind:"mismatch"` with the first 200 characters kept for triage; remaining pending calls at settlement are `kind:"unresolved"`. Each id is reported at most once. An absent or empty command label is inert. **Why detection and not enforcement:** print mode writes tool results without an outcome, and the same non-denial text is produced when upstream rejects a call before the hook runs (`preflightToolCall`: unknown tool `Tool "X" not found`, disabled tool, unavailable tool, `Invalid args for tool "X": …`; `resolveExecution` throws such as the `PathSecurityError` for `.env`-class paths; per-tool synthetic errors; `Tool skipped because a previous tool call stopped the turn.`), when a coexisting PreToolUse hook ahead of the managed block or an upstream permission policy blocks first with its own text, or when a cancel/budget abort lands before the result — none of which executed anything. Swarm subagent calls run in-process and never reach the coordinator's stream, so they are uncovered. No finding proves what filesystem effects occurred.

The client logs `event:"hook_escape"` per finding and returns them on `CliClientResult.hookEscapes`; delivery, teardown, cancellation and budget semantics are untouched. Every managed caller persists them through `observedExecutionFields` into the additive `hook_escapes` column (JSON array: `tool_call_id`, `tool_name`, `kind`, optional `content_excerpt`), prints one stderr `safety hook notice` line (humans), and `status`/`result --json` expose the parsed array (callers); a budget timeout carries them in `error.details.hook_escapes`. The review gate appends the notice to `systemMessage` and otherwise decides as before. Enforcement (stop + fail) is deferred until there is positive execution evidence: the upstream ask, filed as MoonshotAI/kimi-code#4241, is an `outcome: executed|vetoed|rejected` field on print-mode tool records; a plugin-side alternative is a per-job hook trace the hook itself writes before exiting.

Upstream 2.2.0 basis: `features/externalHooks/agent/agentExternalHooksService.ts:162–166` vetoes with `denyToolExecution(reason)`; `agent/toolExecutor/toolExecutorService.ts:419` uses `settleSynthetic(..., 'vetoed')` and `finalizeToolResult` then runs the `onDidExecuteTool` hooks, where `agent/toolDedupe/toolDedupeService.ts` (`appendReminder` from the 3rd identical call, `HANDOFF_VETO_TEXT` at the 12th; `KIMI_CODE_REPEAT_BREAKER` on by default) may decorate or replace the output; `prepareToolCall` settles preflight rejections, `resolveExecution` throws and synthetic errors BEFORE `fireBeforeExecute`; `apps/kimi-code/src/cli/prompt-render.ts:200–207` writes the tool result with unchanged string content and no outcome. The hook writes reason plus newline; upstream trims stderr. Assistant arguments are JSON-stringified from the same object. Re-audit every one of these shapes on each certification.

## 2. Upstream compat and the load-bearing v2 contract

**Release numbering:** plugin versions advance independently of upstream using
ordinary SemVer; a release may deliberately align its number with the kimi-code
version it certifies (2.2.0 certifies CLI 2.2.0), but the number is never evidence —
state the exact certified CLI versions separately. Never reuse a published version or tag. Leading-zero patch numbers
such as 2.0.001 are invalid [SemVer](https://semver.org/); build metadata does not establish upgrade order.
Published versions and tags remain immutable. The source audit, exact-binary controls,
per-operation smoke and full check must pass before extending the runtime table.

Hook-schema review is a separate, narrower gate than execution certification.

### Internal process trust boundary

The managed PreToolUse hook gates model tool calls, not every internal subprocess.
Repository Git configuration and executables are trusted: explorer Git-context
collection can execute configured helpers outside the child tool hook, even
for read-only swarm. Exact 2.1.0 hardens that path; 2.1.1 restores 2.0.2
behavior. CLI 2.3.1 can also run bare `ps` during POSIX session-lock contention
with the child's inherited PATH and cwd; a PATH containing the workspace is
therefore part of the internal-helper trust boundary. Certification does not
claim a hostile-repository sandbox. See
[the safety boundary](safety.md#what-this-safety-story-does-not-cover).


## 3. Credential-bearing config

- **Credential-bearing config**: Treat `~/.kimi-code/config.toml` as credential-bearing (it can hold a BYO-provider `apiKey`) **and `~/.kimi-code/credentials/` (e.g. `kimi-code.json`, mode 0600) as the real OAuth-token store** — the managed login token has lived under `credentials/` since the earliest kimi-code (source-verified), never in config.toml, so it is NOT a per-version migration. For routine status checks, do not read, print, copy, or retain the raw config **or anything under `credentials/`**; use the sanitized `setup --check` or `setup --models [--json]` projection. The model inventory parses config internally and emits only alias/model/provider identifiers, provider types, default selection, and a secondary-settings presence flag. It never emits keys, headers, environment maps, endpoints, OAuth references, or raw parser errors; never reads the OAuth store; and makes no writes or provider calls. If an explicitly authorized diagnosis requires direct inspection of config.toml, restrict it to the plugin-managed hook block and redact all credential material from output; the `credentials/` store is never read or copied.

## 4. Key runtime invariants

- **Session visibility and titles:** successful/terminal user-command synchronization runs after child teardown. For native-v2 state it fills only a missing/blank `lastPrompt` from the actual prompt/objective using upstream-equivalent redaction before the 4,000-character limit, then invalidates the shared index through `sessions/.index-dirty/<sessionId>.<unique-suffix>`. Index invalidation also runs on an idempotent repair, so a prior notification failure can recover. Session journals, cwd, recency and unrelated metadata stay unchanged. Existing custom titles (including native `titleKind` and legacy custom-title fields) and native-generated titles are preserved independently of prompt repair. New native-v2 fallback titles have `titleKind: "replaceable"` and `isCustomTitle: false`; legacy titles retain custom semantics. The native title endpoint is never invoked automatically because it resumes the agent and activates hooks/cron services. Native Desktop generation is an explicit user action or follows a turn in that native UI. Internal review-gate sessions are excluded.

`repair-sessions [--apply] [--all]` reads the current host's job database without migrations. Default scope is the current repository; `--all` expands only to that host store. Eligible sessions have completed native-v2 lineage and no running job in that store. A bounded original spawn prompt must match the stored prompt digest before any metadata change. The default is a dry run. Repair preserves titles and nonempty previews; it never submits a prompt or calls a provider. State/index reads are bounded and no-follow, directory symlinks are refused, state publication is atomic with an optimistic content-conflict check, and dirty-marker failure is reported distinctly. This is not a transaction with native Kimi writers: repair must run while target sessions are idle. No cross-host/native process lock is claimed. Mechanics and UI limitations: [session visibility](session-visibility.md).

- **Model selection**: `--thinking <effort>` requests per-run effort through `KIMI_MODEL_THINKING_EFFORT`, never a CLI flag or saved-default change; omitted flags preserve the operator-owned ambient variable, and resume does not inherit a previous job's request. Providers that are not trait-driven silently ignore it, as does a base level already `off`; an `alwaysThinking` model receives `off` unnormalized. Stream-json carries no thinking deltas (`writeThinkingDelta() {}`), so the plugin cannot verify whether the request was honoured. Omit `-m` for the fresh-session default; resumes keep their session model. Explicit per-run aliases do not change the saved default. `setup --models [--json]` provides a read-only, credential-safe local inventory, not a connection test. Agents resolve natural-language requests to an unambiguous configured alias, never guess or silently fall back; provider setup stays in native `/login` or `/provider`, and saved-default changes require explicit intent via `/model`. Review gate omits `-m` unless `KIMI_PLUGIN_CC_REVIEW_GATE_MODEL` is set. Swarm children may use `[secondary_model]`. See [models.md](models.md).

Model inventory reflects local config and the inherited `KIMI_MODEL_NAME` overlay, not provider reachability or credential validity. It shares Kimi-home resolution with the child, keeps alias keys verbatim, normalizes config fields with upstream spelling rules, refuses ambiguous normalized keys, and suppresses config-bearing error details. Unknown config fields are not serialized. Discovery mode rejects combinations with hook mutation/check flags before invoking setup. Existing task argv and safety gates remain unchanged; only the review gate loses its hardcoded model fallback.

- Subprocess-first. One `kimi -p` prompt runner per job; exact 2.3.2 swarm jobs additionally use the bounded activation lifecycle below, never a second prompt transport or model self-activation. Session id capture is **dual-source for kimi-code compatibility**: kimi-code 0.2.0+ emits a `role:"meta", type:"session.resume_hint"` record on stdout in stream-json mode once per prompt run at session END (after `runPromptTurn` settles), carrying a `session_<uuid>` token; kimi-code 0.1.x emitted a plain `To resume this session: kimi -r <uuid>` line on stderr. The cli-client consumes both channels — first-announce-wins, pinned, idempotent — and filters the meta record out of the consumer-facing records[] surface so commands iterating assistant/tool prose don't see it. The stderr regex anchors to line bounds and requires a full UUID payload (both bare and `session_<uuid>` alternations) so a malformed line can't pin a garbage id. 0.1.x users on text-output mode (or any future kimi version that re-introduces stderr emission with the new shape) keep working. Captured id round-trips verbatim via `kimi -r <token>` — we treat it as an opaque identifier whose shape may evolve again.
- **Same-job swarm activation (exact 2.3.2):** upstream removed model-started AgentSwarm from fresh print sessions, so `runtime/swarm-activation.ts` starts the exact planned CLI as `web --no-open --host 127.0.0.1 --port 0 --log-level error`, with the same environment as the print spawn and all execution-plan/no-plan/trusted-root checks. Authenticated loopback `/meta` must report backend v2, exact planned version and no auth bypass. The plugin creates the session at the actual swarm/worktree cwd, binds explicit `-m` or the effective default (the environment alias is `__kimi_env_model__`; `/config` is the secrets-redacted projection and only `default_model` is consumed), sets `permission_mode:auto` and `swarm_mode:true`, verifies `/status` also has plan off and the expected model, shuts down and requires main-journal `swarm_mode.enter` with `trigger:"manual"`. It then passes that same-job id as `resumeSessionId` through ordinary `kimi -p`; `kimi_session_id_source` is `preactivated`, the returned print id must match, and the usual first-line `system.version` and final no-plan journal checks still apply. A second bounded lifecycle sets swarm false and requires a new `swarm_mode.exit`. Activation consumes the operation budget. `runSwarm` is the sole session-deactivation owner; preactivation never starts a rollback server. Normal deactivation uses the remaining budget, while failure recovery has a separate two-second cancellation-aware bound and is never retried. Print/session failures stay primary, with exit codes and cleanup diagnostics preserved. Phase stays `turn-running`, preserving the 60-second MCP attachment contract. Cancellation aborts the owned lifecycle and never starts a fresh cleanup server. Every post-mutation failure retains the session identity; process/group uncertainty is marked without inventing an ID; process groups are rechecked after teardown, unknown survivors are unverified, unproven groups are never signalled, and a same-PID/start-token process that changes PGID remains active but is not a validated signal target. Timeout reclassification applies only when cleanup is the primary failure, and `cleanup_error.cancelled` reflects actual user cancellation rather than budget expiry. Success cannot complete when cleanup is unverified: retain raw output and structured `cleanup_error`, and preserve the write worktree for recovery. Every owned process tree is identity-checked and quiescent before cleanup is claimed; a parent exit alone is not proof. A hard kill can leave manual state in a plugin-created session, so an unconfirmed cleanup never reports success. Swarm certification requires distinct child journals and correlates each assigned Write/Edit `path` and `toolCallId` with its own result; an AgentSwarm call record, aggregate denial or coordinator-only patch is not fan-out evidence. Older certified versions remain direct `kimi -p` without activation processes.

- Hook verification is **strict-by-default and exact**: `verifyHookInstalled` reconstructs the canonical shell command from env via `runtime/hooks/install-paths.ts::tryBuildExpectedHookCommand` and equality-checks it against the current host's installed command. Setup/check first parse the **complete** TOML with vendored `smol-toml@1.9.1` with upstream security fixes included (no backport needed), then strictly validate every configured hook against kimi-code's config schema before applying the plugin's managed-block grammar; malformed unrelated config therefore cannot be hidden by a locally valid managed block. (The strict validation is hooks-scoped by design — unknown top-level tables such as 0.39's `[swarm]`/`[experimental]` parse and are tolerated, so new upstream config sections never lock out setup/check.) Substring and partial-parse paths are forbidden because crafted commands or malformed foreign tables can otherwise bypass setup-time safety checks. The canonical command bytes still have one source in `install-paths.ts`, consumed by install, check, the shell probe, and the per-command verifier. **Markers are NOT durable:** kimi-code persists its config via smol-toml `stringify(parse(...))` on every login/settings write, which deletes ALL comments — including the managed-block BEGIN/END markers — while the `[[hooks]]` table (data) survives and keeps enforcing. `evaluateInstalled` therefore falls back, ONLY from the absent state, to a marker-less table that is our clean enforcing hook. **That decision is made with the REAL `smol-toml` parser** (`hasCleanEnforcingHookEntry`), not a line scanner: it strips managed-block lines (host isolation), parses the remainder, and accepts only a `hooks[]` entry with `event="PreToolUse"`, `command===` the byte-exact canonical command, **NO `matcher` in any TOML spelling** (a matcher can disable/narrow the hook — `new RegExp("*")` throws → hook off → auto-approve), and no keys beyond `{event,command,timeout}`. Never regress this to a line scanner: one has demonstrated blind spots (a matcher hidden after a blank line, behind a quoted `"matcher"` key, or past a multiline array value); the parser is immune. `findBareApprovalHookTables` remains ONLY the conservative line-based PRUNE scanner. Orphan pruning (`findUnmanagedApprovalHookBlocks`) is **host-scoped** via `hostIdFromHookCommand` plus an `alsoMatchCommand` byte-exact clause — one host's install/scoped-uninstall/`--uninstall` never removes another host's marker-less live hook yet always reclaims its own by exact command even under a host-id override (`--uninstall --all` is the explicit every-host sweep; hand-rolled hooks are never touched). Invariants to re-verify each audit: the installed check stays **parser-based, matcher-rejecting, byte-exact, absent-state-only**; the prune stays host-scoped.
- **Serialized config mutation.** Install and uninstall hold a private adjacent `config.toml.kimi-plugin-cc.lock` across the complete read-modify-write transaction. Candidate publication is atomic; lock reads are no-follow/nonblocking/regular-file-only and capped; acquisition is bounded; live owners are never stolen; stale recovery uses an ABA-safe recovery lease; and inode/token ownership is rechecked before mutation or removal. - **Host-scoped managed blocks.** Claude Code and Codex install the plugin to **different, version-stamped paths** (`~/.claude/plugins/cache/…` vs `~/.codex/plugins/cache/…`) but share one `~/.kimi-code/config.toml`. The managed block is therefore keyed by a **host id** — the marker carries a `:<host-id>` suffix (`# === BEGIN kimi-plugin-cc-managed:claude-code (vX) ===`). **Never collapse back to one shared block:** a single un-suffixed block was exact-matched to the running host, so `/kimi:setup` (Claude) and `$kimi-setup` (Codex) overwrote each other and the loser's write-commands refused with "hook path drift." `resolveHostId` (`install-paths.ts`) derives the id *version-independently* from the hook path (`.claude`→`claude-code`, `.codex`→`codex`, else `host-<sha1[:16]>`; `KIMI_PLUGIN_CC_HOST_ID` overrides), so a plugin upgrade **refreshes** the same host's block instead of accumulating one per version. `parseManagedBlock(contents, hostId)` resolves to the current host's own suffixed block (a lone legacy un-suffixed block is adopted as a fallback); `evaluateInstalled` **requires** `hostId` and keeps the per-host exact-equality contract. `runInstall` upserts only this host's block, converts a matching legacy block in place, and prunes orphaned marker-less approval-hook `[[hooks]]` (via `findUnmanagedApprovalHookBlocks`/`isOurApprovalHookCommand` — strict: canonical two-single-quoted-token command whose script is `approval-hook.js` under a kimi-marketplace/kimi-plugin-cc tree, so a hand-rolled hook is never removed). `runUninstall` is host-scoped by default; `/kimi:setup --uninstall --all` removes every host's block. Enforcement stays correct under coexistence because kimi-code fires every `[[hooks]]` and aggregates **any-block-wins** — the current host's live hook always denies; a stale *other*-host path fails open harmlessly; a drifted *own* block is caught at the per-command verify gate (prompts a re-setup for that host only). Invariant to re-verify: the exact-equality check is per-host, and no install/uninstall path ever mutates another host's block.

- **`/kimi:swarm` = read-only parallel fan-out.** Exposes kimi-code 0.12.0+'s `AgentSwarm` tool so Kimi fans a **read-only** review out across subagents (one per target) and consolidates the findings. `runtime/commands/swarm.ts` spawns with `commandLabel: "swarm"` — a hook label (`runtime/hooks/approval-policy.ts`) that allows the read-only tool set PLUS the exact tool name `AgentSwarm` (verified `readonly name = 'AgentSwarm' as const`), and nothing else (the singular `Agent` tool is denied). See `docs/safety.md` § "Read-only swarm".

Gated to kimi-code **≥ 0.18.0** (the hard `KIMI_CODE_AGENT_SWARM_MAX_CONCURRENCY` cap — below it a write fan-out has no peak bound), a git repo with a **born HEAD** (`WRITE_SWARM_NOT_A_REPO`/`WRITE_SWARM_NO_HEAD`), with a **loud dirty-tree warning** (worktree is off HEAD, so uncommitted work is not included). Keep that asymmetry visible in the agent docs. **A model-invocable `kimi-swarm-write` agent** wraps this command: auto-dispatch widens no write surface and removes no bound — it runs the identical `runSwarm --write` (patch-only; the plugin never applies/commits; worktree confinement + managed hook + `--budget` + default `--max-concurrency` 1 + hook-required all hold), making it a *less* dangerous agent than the write-capable `kimi-pursue` (which writes directly to the workspace). - **Timeout session recovery:** `CliClientResult.spawnedAt` is taken immediately before spawn and `settledAt` only after owned teardown. Native-v2 budget timeouts without an announced or already-known ID scan `sessions/*/session_*/state.json`, capped at 65,536 visited entries across both levels (a pathological-tree guard, not a size budget: the reference host held ~2,500 entries when written and grows by one per run, so the preflight's 4,096 would have disabled recovery), 1 MiB per `state.json`, the first 4 MiB of each journal (the prompt is argv-bounded; a prefix cut mid-line is never parsed) and 64 MiB total, all regular no-follow files. Candidates require version 2, an absolute cwd whose realpath equals the job cwd, creation time in [spawnedAt, settledAt] (no pre-spawn slack: the child writes `createdAt` after the parent stamped `spawnedAt` on the same clock, so causality orders them), a matching `session_[0-9a-f-]{36}` directory/id, no other job row on this host using that ID (global indexed lookup, rechecked atomically when persisting recovery), AND a main journal (`agents/main/wire.jsonl`) whose FIRST user message (`context.append_message`, `message.role:"user"`) carries a text item whose sha256 equals the job's `prompt_digest` — the exact `-p` argument (`firstUserMessageMatches`). The digest is the content binding that makes attribution proof: time and cwd alone would admit a concurrent interactive session, another host's finished job (stores are host-local) or a `state.json` planted by repository code under rescue, and a planted clean journal would replay attacker-written turns into the next resume. The digest alone is not unique (the same prompt can run twice), so the window and the exactly-one rule remain. Malformed JSON is skipped. Exactly one candidate is required; none, ambiguity, capped or unreadable enumeration never selects a newest session. Recovery is skipped (`engine_unobserved`) when the run never emitted the `system.version` marker, since resume would refuse the row as lineage-unknown. Error details expose `session_recovery` on refusal (`none`, `journal_missing:<n>`, `digest_mismatch:<n>`, `ambiguous:<n>`, `enumeration_capped`, `unreadable`, `engine_unobserved`, `persistence_failed`; a failed write of an ANNOUNCED id is reported as `session_id_persistence` instead), or the recovered ID and source after persistence. Symlinked and dot-prefixed entries inside the store (`.index-dirty`, `.index-cache`) are skipped uncounted, never followed; only a symlinked `sessions` root, or a directory swapped for a symlink between enumeration and descent, refuses as `unreadable`. Session directories whose mtime predates the spawn are skipped before any read. Recovery never creates observed-engine evidence: a resumed recovered ID still passes `assertPersistedResumeLineage` and every raw wire-journal plan-taint scan. Cancellation, non-timeout failure and teardown rejection do not recover IDs.
- Config writes preserve mode 0o600. `writeConfigAtomic` chmods the temp file before rename so the final inode never exists at a wider mode, matching the user's existing kimi-code config permissions (the file holds API keys + tokens).


## 5. Plugin data ownership

`runtime/plugin-data.ts` resolves the parent of the existing `kimi-plugin-cc/` state directory. `KIMI_PLUGIN_CC_DATA` is an explicit operator override and must be absolute and nonempty. It takes precedence over both shared host variables.

For a standard `plugins/cache/<marketplace>/kimi/<version>` install, the runtime uses its own loaded module location and package manifest to identify the expected data directory. It does not use the shared `CLAUDE_PLUGIN_ROOT` or `PLUGIN_ROOT` values to establish that identity. Claude uses `plugins/data/kimi-<marketplace>` (with the [documented identifier sanitization](https://code.claude.com/docs/en/plugins-reference#persistent-data-directory)); the bundled Codex package uses `plugins/data/<marketplace>-kimi`. Updating the version does not change that directory. First-run directory comparisons resolve the nearest existing ancestor, so a symlinked home remains valid before its data directory exists. Dangling links, unreadable ancestors, and non-directory ancestors do not establish equivalence.

Without an explicit override, a shared `CLAUDE_PLUGIN_DATA` or `PLUGIN_DATA` that disagrees with the expected directory raises `PLUGIN_DATA_CONFLICT` before the runtime creates directories or opens the job store. The error includes `expected_data_root`. Remove the polluted variables to use that location, or deliberately set `KIMI_PLUGIN_CC_DATA` to an existing custom data parent. The override points to the parent of `kimi-plugin-cc/`, not the database or that subdirectory itself.

For checkouts and nonstandard install layouts, ownership cannot be inferred. One shared value, or two values naming the same path, remains supported for compatibility; the caller is responsible for that directory. Conflicting values refuse instead of choosing one silently. Use the namespaced override for custom launchers exposed to shared-environment pollution. A bare shell launch can use the Codex data fallback under `CODEX_HOME` or `HOME`. Without a home or an explicit data source, it refuses instead of choosing a shared `/tmp` directory. Direct runtime calls with no data source still refuse.

No resolver path copies, moves, merges, or deletes existing state. Legitimate default directories and explicitly selected custom directories retain their config and jobs. Previously misplaced state is not discovered or migrated automatically. Detached workers receive the parent's selected absolute root through the namespaced variable, so a cwd change cannot redirect the worker's store. Stop-hook resolution failures produce a visible skip without opening a store or invoking Kimi.

This is protection against accidental shared-environment collisions, not a security boundary against a caller who controls the plugin package or its namespaced override. Installed subprocess regressions cover both host layouts, foreign-directory noncreation, existing settings/jobs, custom overrides, and the Stop hook. A background-job regression checks that foreground lookup and detached work share the selected store.

Plugin-only maintenance releases may advance the plugin patch while the certified CLI table stays unchanged. Published plugin versions and tags are immutable; a later CLI certification must use an unused plugin version.

### Structured print-mode refusals

CLI 2.3.0 emits a role-less `{type:"error", code, message, details}` record for an occupied session and exits 4, without a stderr message. The parser retains only bounded `code` (200 characters) and `message` (4,000 characters) on `CliClientResult.cliError`, first record wins; holder metadata and session IDs are discarded. This record never enters prose, callbacks or session lineage, and never overrides the process exit status. Native-v2 marker-first verification still applies. Nonzero failures expose the diagnostic through `CLI_NONZERO_EXIT.details.cli_error` and its message. Malformed error shapes remain diagnostic-only.
