## 1.9.7 — 2026-08-08

**Makes hook refusals self-healing for every caller and startup failures self-diagnosing.** No safety-policy, permission, concurrency, budget, allowlist, or `KIMI_TESTED_MINORS` change; experimental-v2 remains fail-closed refused.

- **The re-pin protocol rides the refusal message.** Every `*_HOOK_NOT_INSTALLED` refusal now appends a single-source caller protocol (`hookRefusalRetryProtocol`, `runtime/hooks/install.ts`, consumed at all five model-spawning refusal sites): on `retryable_after_setup: true`, run the embedded resolved `companion.sh setup` and retry the refused command once only on exit 0; anything else — or a second refusal — surfaces. Slash-command callers now self-heal after a plugin update exactly like the agents (whose `agents/*.md` contract is unchanged), completing step 3 of the hook-pin durability spec's recommended path for all surfaces with zero duplication in the 13 surface files — an earlier draft that pasted the paragraph into each command was reverted for exactly that bloat.
- **`auth.login_required` is classified as auth, not startup.** kimi-code's logged-out OAuth store (`auth.login_required: OAuth provider "managed:kimi-code" requires login…`) reaches the classifier inside the `CLI_NONZERO_EXIT` message (cli-helpers embeds the stderr tail); a new branch ahead of the generic nonzero-exit case maps it to `*_KIMI_AUTH_UNAVAILABLE` with a "Run `kimi login`… `/kimi:setup` does not repair auth" remedy. Trigger incident: 2026-08-08, an out-of-band kimi background auto-upgrade (0.31.1→0.34.0) invalidated the token and the plugin's startup-failed advice misdirected to setup.
- **Wrapped startup failures keep their cause.** `classifyManagedCommandFailure` threads `availability`, `cause_code`, and a tail-truncated (2 KB) `cause_message` into `RuntimeError.details`, so the underlying stderr survives on the foreground `details:` JSON line and in the SQLite job row. Previously the cause lived only on the unserialized `cause` chain — invisible to LLM callers on every channel (LLM-caller discipline).
- Tests: login classification, details threading, tail truncation, and the review-gate warning path; full `bun run check` green (692 pass / 0 fail).

## 1.9.2 — 2026-07-25

**Agent-facing docs release. No runtime change.** Detaching the caller's shell call is now the documented default for the two write-capable surfaces, the cancel path is corrected to the form that can actually execute, and the harness interrupt contract is measured rather than assumed.

- **The bug this fixes is a doc bug with real consequences.** A dispatching agent refused `/kimi:swarm --write` outright, reasoning that the agent doc forbade `run_in_background: true`, `--budget` defaults to 30m, and Claude Code caps a foreground Bash call at 10 minutes. Every premise was true; the conclusion was not. The docs had conflated the runtime's rejection of `--background`/`--wait`/`--fresh`/`--resume` (real, unchanged) with a doc-level rule against the *caller* detaching its own shell call — a rule motivated by watchability, not enforced by anything. `swarm-write` and `pursue` now document caller-level detaching as the default. Read-only swarm's foreground default is unchanged and deliberate.
- **What actually bounds these surfaces** is the index-0 PreToolUse hook, the workspace allowlist, no-git-mutation, patch-only worktree confinement (swarm-write), and the mandatory finite `--budget` — all runtime-enforced, none dependent on a human watching. A blocked foreground call is *worse* oversight: it freezes the dispatching agent for the whole run, so it cannot report progress or cancel on request.
- **The first draft of the cancel path was falsified by review, and is corrected.** It told agents to "keep the `job_id` from the launch output and run `companion.sh cancel <job-id>`". That flow cannot execute: `pursue.ts`/`swarm.ts` mint the id with `randomUUID()` and emit nothing at launch, so a detached caller holds a host task id and the plugin id first appears in the final report. The working path is the **no-id** form — `companion.sh cancel` resolves `findLatestJob({runningOnly:true})` for the repo — which also removes the UUID from the human path entirely. Documented limit: with several runs in flight it takes the most recent, so a multi-run session confirms first.
- **Interrupt signal contract measured** (macOS, Claude Code): foreground Esc and `TaskStop` on a detached call both deliver a trappable SIGTERM **process-group-wide**, then SIGKILL after **~1.35s** (samples 1.34s / 1.36s). Two consequences. Group delivery reaps detached Kimi descendants along with the companion, so the "surviving child keeps writing to the real tree" risk raised against backgrounding `pursue` does not exist. But ~1.35s is shorter than `cli-client.ts`'s 1500ms child escalation *alone*, before quiescence and `git diff --binary` capture begin — so a hard interrupt can kill the companion mid-teardown and **lose the write-swarm patch**. `companion.sh cancel` signals from a separate process not racing that deadline and is the work-preserving stop. The margin is thin; re-measure on harness changes.
- **`pursue` is not `swarm-write`.** An adversarial review caught the first pass flattening a real asymmetry: swarm-write's edits are worktree-confined and return as a discardable patch, while pursue's land in the user's real tree and a cancel stops further work **without rolling back** what is already done. Both now default to detached callers; only pursue carries the non-rollback warning.
- **Seven surfaces, one contract — and they had already drifted.** The cancel correction initially landed in AGENTS.md and both Claude agent files but missed `scripts/surface-registry.ts`, so the repo told Codex to do the thing the same commit called impossible. Also fixed: `agents/kimi-pursue.md` contradicting itself four lines apart, `commands/{pursue,swarm}.md` routing a stop through an unobtainable id, `commands/cancel.md` documenting only the id-shaped form, `commands/swarm.md` flattening read and write swarm into one detach rule, and `docs/safety.md` claiming unqualified patch-capture-on-cancel that does not hold under a harness interrupt.
- **Doc hygiene: version archaeology moved out of the reference docs.** `AGENTS.md` § Releasing requires one current headline with per-version history in CHANGELOG/ROADMAP; the reference docs had drifted from that, and this session's own edits made it worse. Audited by three parallel read-only agents, applied by hand, with the rule that no fragment could be dropped until it was proven recorded elsewhere. One was not — pre-1.0 `v0.2.3` — and was added to "Older releases" below before the trim. Regression-preventing rationale was kept and sharpened into prohibitions ("never re-merge the two flags", "never collapse back to one shared block", "never regress this to a line scanner"). Also drops a stale "verified byte-identical through 0.12.0" that under-reported the tested range by 17 minors.
- **The Releasing instruction itself was ambiguous** about what a headline is, which is how the accretion kept happening. It now says the Version headline states a present-tense contract an agent must not regress — not what the release did — with an example of each. The 1.9.1 hook-pin durability contract is retained as the headline deliberately: it is still standing, and it is the only place that contract is written down.
- **No upstream-compat change.** `KIMI_TESTED_MINORS` unchanged through `{0,29}`; no kimi-code re-certification, no runtime code touched.

## 1.9.1 — 2026-07-25

**Closes the background hook-enforcement test gap that let the v1.9.0 regression reach pre-release review, and adds a narrow verification-time probe that the pinned Node interpreter is still executable. Deliberately scoped: this is NOT a fix for a silent bypass — the wider rationale it was first written with was refuted by review and is recorded here so it is not revived.**

- **Test gap closed (the substantive change).** Every background test set `KIMI_PLUGIN_CC_SKIP_HOOK_CHECK=1`, and the one worker-refusal test drove `executeAskJob` **in-process** — so no test had ever run a real detached worker with enforcement on. That is precisely why v1.9.0's `spawn(process.execPath)` regression, which would have made every background rescue/ask refuse forever, was caught by a model review instead of by CI. New `tests/runtime/background-hook-enforcement.test.ts` runs the companion CLI as a real node subprocess invoked **through a symlink**, with **no** `KIMI_PLUGIN_CC_NODE_BIN` override, and asserts the spawned worker's own hook check agrees with the parent's pin. Confirmed to catch the original bug by reverting it: the job fails with `drift_axis: "node-bin"`, expected `…/Cellar/node/26.5.0/bin/node` vs. installed stable symlink. This could not live in the existing suite — with an override, spawner and verifier agree *by construction* (the buggy code honored the override too), and reproducing the no-override path needs a real node parent, impossible under `bun test` where `process.execPath` is bun.
- **The argv0 premise is now measured, not assumed.** v1.9.0's regression test fed the expected value in as the child's `argv0` rather than observing one, so it assumed the OS behavior the whole fix rests on. A real child now reports its own `argv0`/`execPath` (via `tests/helpers/print-node-pin.mjs`, which imports the **compiled** `dist/` a worker actually loads) and proves `spawn()` passes argv[0] verbatim without resolving symlinks.
- **Interpreter executability probe (`access(nodeBin, X_OK)`), honestly scoped.** `verifyHookInstalled` already confirmed the hook *script* was readable; it never confirmed the *interpreter* was runnable. The predicate it covers is narrow and exact: **config and expected command still match byte-for-byte, yet the Node token embedded in that command fails `X_OK` at verification time.** Reachable three ways — an absolute `KIMI_PLUGIN_CC_NODE_BIN` naming an already-dead binary that is not the running interpreter (e.g. an `nvm uninstall`ed version, via a direct `node dist/companion.js` that bypasses `companion.sh`'s exec+version gate); or **post-launch mutation on the default path**, where the interpreter is valid at launch and is then `chmod -x`'d (`realpath` still resolves, argv0 is retained, bytes unchanged) or removed (fallback to `execPath`, identical spelling in `argv0 === execPath` layouts). In each, the old behavior was `installed: true` → `/bin/sh -c` exits 127 → kimi-code reads any non-2 exit as ALLOW. Setup's stronger *execution* probe is not a substitute: it runs at install/`--check`, whereas this reruns before every model spawn and so catches degradation since the last probe.
- **What it explicitly does NOT do** (recorded because the first draft claimed otherwise, and a wrong comment about the threat model is worse here than wrong code). It does **not** catch a dangling Homebrew symlink: a dangling symlink cannot be exec'd and `command -v node` skips it, so `companion.sh` resolves a *different* node, the expected command is recomputed from the live process and changes, and plain byte-exact equality refuses first — with a **recoverable** drift that `/kimi:setup` converges. It likewise does not catch the 2026-07-25 dead-node zombie (a config pinning `~/.hermes/node`), which is a byte mismatch. And it proves the exec bit only — not a working Node, not the right arch, not >= 22.5. The bypass is **narrowed, not closed**.
- **`nodeBin` is derived by parsing the built command back, never by re-resolving.** `tryBuildExpectedHookCommand` now returns the interpreter token, obtained via `parseHookShellCommand(command)` — the exact inverse of how it was built — so it is byte-identical to what the config is compared against **by construction**. Re-calling `resolveNodeBinary` would have been a latent reintroduction of the very bypass being fixed: its no-override path runs `preferStableNodePath`, which does `realpath` I/O and is therefore **not** a pure function of `env`. Had the pinned symlink been unlinked between the two calls (what `brew upgrade node` does), the command would pin the symlink while the probe checked the stale realpath — which may still exist — blessing a hook whose real interpreter was gone. Caught in review before shipping; `tryBuildExpectedHookCommand`, previously untested, now pins this identity.
- **Machine-readable refusal discriminator.** This is the one refusal whose remedy is *not* "run /kimi:setup" — setup cannot repair a broken Node — yet it emitted a `{config_path}` payload byte-identical to four other refusals. It now carries `refusal_kind: "node-bin-not-executable"` plus `node_bin`, per LLM-caller discipline. It can never co-occur with `drift`: drift requires the equality check to **fail**, this requires it to **pass**, so the new refusal cannot displace a recoverable path. ## 1.9.0 — 2026-07-25

**Stops the recurring "run /kimi:setup" nag at its source: the canonical hook command no longer embeds the Node *version*, and a refusal caused by a moved hook path now carries a machine-readable drift axis so an agent caller can re-pin and retry once. No self-writing verifier — that design was proposed, adversarially reviewed twice, and rejected.**

- **Root cause.** "Installed" is byte-exact equality between the config's `command` and a freshly rebuilt canonical command — the strictness that killed the old `true # …approval-hook.js` substring bypass, and it is not negotiable. But that command embedded **two independently version-stamped paths**: the Node binary (`process.execPath` resolves the Homebrew symlink to `…/Cellar/node/<version>/bin/node`) and the version-stamped plugin install dir. `brew upgrade node` invalidated **both hosts at once**; a plugin update invalidated one. Routine maintenance therefore read as "the plugin keeps breaking." Diagnosed live 2026-07-25: Codex auto-updated 1.8.7→1.8.8 and deleted the old dir while the config still named 1.8.7. A June config backup holding `node/26.0.0` and `node/26.3.0` side by side shows the Node axis had already fired before.
- **Node axis fixed at the source (`preferStableNodePath`).** `resolveNodeBinary` now prefers `process.argv0` — the path the interpreter was actually invoked with, which `companion.sh` resolves through the stable `/opt/homebrew/bin/node` symlink — but **only when it is absolute AND `realpath`-identical to `process.execPath`**. That guard is the whole safety argument: the substitution provably cannot select a *different* binary, only a more stable *name* for the one already running. Any doubt (relative argv0, `realpath` throw, different target) falls back to `execPath`. Byte-exactness, absoluteness, and the shell probe are untouched. Side benefit: hook and companion now ride the same interpreter by construction — previously the companion could run a new Node while the hook stayed pinned to a Cellar path `brew` had already deleted, which spawns nothing and (exit 127) **reads as ALLOW**. nvm/asdf/mise expose version-stamped paths directly, so `argv0 === execPath` there and behavior is unchanged, not worse.
- **Structured drift signal.** `InstalledCheck.drift` / `HookInstallStatus.drift` (`{axis: "hook-script" | "node-bin" | "both", installedCommand, expectedCommand}`) is populated **only** when a structurally sound block's command names different paths, and is forwarded into every refusal's `RuntimeError.details` via the shared `hookRefusalDetails`. Strictly advisory: derived *after* byte-exact equality has already failed, it can never influence `installed` — the same contract `nodeExists` classification has always had. Refusals that are *not* re-pin-recoverable (unresolvable command, unreadable config, invalid hook set, duplicate/orphan markers, missing script) carry **no** drift, so a caller cannot mistake them for retryable. The `absent` + stale-bare-table case is classified too — that is the **common** real-world shape, since kimi-code strips markers on every login write and a plugin update then moves the path (both at once is exactly the 2026-07-25 incident).
- **The caller heals it, not the callee.** All seven model-spawning agents now read `drift_axis`: on `"hook-script"` (`retryable_after_setup: true`) they run `/kimi:setup` for that host and retry **once**; on anything else they surface the refusal and stop. Repair stays a **visible, permission-gated action in the transcript**, taken by the host model — not a silent mutation of a security surface. `"node-bin"`/`"both"` are deliberately never auto-retried: a moved interpreter may be *gone*, and that is a real enforcement gap, not a moved file.
- **Auto-repin REJECTED (recorded so it is not re-proposed).** An in-verifier self-repair was fully specified, then rejected by two independent adversarial reviews. Four defects were mechanically confirmed: (1) **self-deadlock** — the repin path takes `withKimiConfigLock`, then the install transaction takes it again, and the lock has no reentrancy check (staleness is `!isProcessAlive(owner.pid)`, and the owner is us), so every attempt spins 10s and throws; (2) the "target cannot be steered" premise is **false** — `KIMI_PLUGIN_CC_HOOK_SCRIPT`/`NODE_BIN`/`HOST_ID` override resolution, and every gate reads the same env, so they are self-consistent by construction and supply no independent evidence; (3) **no version-monotonicity bound**, so a surviving old session could pin the *global* block to a pre-1.0.3 hook carrying the CRITICAL exec-delegation bypass — the exact outcome that argument was built to prevent; (4) a **write→spawn TOCTOU** in which a stale session repins to a deleted path inside another session's spawn window, yielding exit 127 → ALLOW → an unenforced `rescue` run. The v1.8.0-lock rebuttal was also rationalization: v1.2.1's objection was *authorization* + *detection*; a lock provides *atomicity*, making an unauthorized write correctly serialized. Full analysis, including why **content/hash verification also fails** (the proposal hashes `approval-hook.js` — 4,325 of 55,661 bytes, 7.8% of enforcement code — while the v1.0.3 CRITICAL fix lives in `rescue-approval.ts`; and hook/companion are two halves of one wire protocol a global version floor cannot express) is preserved in `.claude/hook-pin-durability-spec-2026-07-25.md`.
- **Migration.** The canonical command changes, so **every existing install drifts once** on upgrade and needs one `/kimi:setup` per host. Enforcement is not lost meanwhile — the old block keeps firing; the plugin refuses to *spawn* until re-pinned. The drift is classified as the benign case (see below) and the agents self-repair it.
- **Migration message is honest about the cause.** `describeHookCommandDrift` now recognizes when two node paths name the **same file** (`realpath`-compared) and says so — *"Node path spelling changed … these are the SAME interpreter reached by different paths … your Node did not move"* — instead of the pre-existing wording that blamed "a Node version-manager switch between runs", which would have misled every upgrading user. A **gone** interpreter still takes precedence and still reports "no longer exists": that is the unambiguous danger signal and must never be softened into a benign re-pin.
- **Pre-release review round (Kimi + Opus, converging independently).** Three defects were found and fixed before tagging:
  - **CRITICAL — background rescue/ask would have refused permanently.** `startBackgroundJob` spawned the worker with `process.execPath`, so the child's `argv0` was the fully symlink-resolved (version-stamped) path, while setup — running through `companion.sh`, which execs `$(command -v node)` — pinned the stable symlink. The worker re-verifies the hook (deliberately, so a background job cannot outlive or bypass the check), rebuilt a *different* expected command, and `/kimi:setup` could never converge the two sides. Foreground commands were unaffected, which is exactly why it would have shipped. Now uses `preferStableNodePath` for the no-override default — deliberately **not** `resolveNodeBinary`, whose absolute-path requirement is the *hook-pin* contract, not the *spawn* contract (spawn resolves a bare name via PATH). Regression test added.
  - **The signal never reached the caller.** Agents were told to branch on `drift_axis`, but `formatError` dropped `details` entirely and the failure artifact rendered only code/stage/message — so the field existed only in the SQLite row, reachable via `result --json` for background jobs and *lost outright* for foreground ones. `formatError` now serializes details as one deterministic JSON line (non-serializable values can never suppress the error itself), and the artifact renders a sorted `### Details` section.
  - **The retry could walk past a proven-dead hook.** `/kimi:setup` **install** exited 0 even when its probe *failed*, and only `check` exited nonzero. Since an agent now keys its retry on that exit code, a hook that is byte-exact and readable but cannot deny — a truncated `approval-hook.js` (iCloud sync has done this in this repo), or a half-extracted plugin cache — would pass `verifyHookInstalled` and the command would run unenforced. Any failed probe now exits nonzero, and the agents retry only on a clean exit. `probe: "skipped"` (uninstall) is untouched.
  - Also fixed: agents were told to run `/kimi:setup`, a slash command a `tools: Bash` subagent cannot invoke — they now call `${CLAUDE_PLUGIN_ROOT}/scripts/companion.sh setup`, the same surface the command wrappers use; and `retryable_after_setup` contradicted the new same-file finding (prose said "benign, expected" while the field said "do not retry") for the single most common refusal this release creates. Retryability is now "every differing token is benign": a moved script, or a node token whose spelling changed but still names the same file. A node token naming a **different** file is still never retryable.
- **No upstream-compat change.** `KIMI_TESTED_MINORS` and all kimi-code surface reasoning are unchanged; this is a plugin-side durability fix, not a kimi-code certification.

**Survive kimi-code config rewrites: markers are comments, and kimi-code deletes every comment on every config write. Verification now falls back to byte-exact content identity, and orphan pruning is host-scoped — ending the cross-host setup "seesaw" and the false "not installed" after every kimi login.**

- **Root cause (live-captured during diagnosis, 2026-07-16).** kimi-code persists `config.toml` via `stringifyToml(configToTomlData(...))` (`packages/agent-core/src/config/toml.ts`; login flows call it via `managedAuth.ts`) — smol-toml's stringify cannot represent comments, so **every login/settings write deleted both hosts' `# === BEGIN/END kimi-plugin-cc-managed ===` markers** while the `[[hooks]]` tables (data) survived and kept enforcing. ## 1.4.0 — 2026-06-20

**Write-capable swarm (`/kimi:swarm --write`): parallel code-editing in a throwaway worktree → reviewable patch.** Adds the first WRITE mode to swarm. Where read-only swarm fans `explore` subagents out for review, `--write` runs the coordinator and `coder` (write-capable) subagents inside an **ephemeral detached git worktree off the user's HEAD**, lets them edit disjoint targets there, captures the result as an applyable `.patch` artifact, and removes the worktree. **The user's real working tree is never touched, and the plugin never applies or commits — the main Claude thread owns the merge** (the load-bearing "main thread owns git" invariant). Design A (one worktree for the whole swarm) — kimi-code's `AgentSwarm` spawns subagents in-process sharing the coordinator's cwd (`subagent-host.ts:362`), so per-subagent worktrees are impossible without abandoning `AgentSwarm`; the single throwaway worktree IS the blast radius. Human-only (`disable-model-invocation: true`); there is no `kimi-swarm-write` agent yet.

This shipped after a **3-way adversarial spec review** (safety / kimi-contract / convention lenses). Two reviewer blockers were resolved by direct verification against the vendored kimi-code 0.18.0 source: (1) the hook-payload `cwd` for an in-process subagent equals the coordinator spawn cwd (one `HookEngine` per session, `cwd: kaos.getcwd()`, `session/index.ts:178`), and (2) **swarm subagents use the standard permission stack — no deny-all** (the lone `DenyAllPermissionPolicy.unshift` is inside `startBtw()`, the side-question path, NOT the swarm spawn path), so a `coder` subagent's writes actually land and are gated solely by our hook. (Fixed a stale `kimi-version-probe.ts` comment that had mis-cited swarm subagents as inheriting deny-all.)

- **New hook label `swarm-write`** (`runtime/hooks/approval-policy.ts`): allows `AgentSwarm` + the read-only set; routes write/edit/shell through the **rescue allowlist verbatim** — but scoped to a **forge-proof trusted worktree root** (`KIMI_PLUGIN_CC_WORKSPACE_ROOT`, exported by the same plugin spawn that sets `KIMI_PLUGIN_CC_CMD`), NOT the hook payload `cwd`. The model inside kimi cannot set an env var on its own process, so confinement does not depend on upstream payload-cwd semantics. **Fail-closed**: a missing trusted root denies all writes. git mutation and the singular `Agent` tool stay denied.
- **Worktree lifecycle** (`runtime/git.ts`): `createEphemeralWorktree` (off HEAD, under the plugin's own `worktreesDir` — never inside the user repo), `captureWorktreePatch` (`git add -N` intent-to-add + `git diff --binary`, **untruncated**, so new files are captured WITHOUT writing loose objects into the shared object DB — keeping "plugin never mutates git state" literally true), `removeWorktree` (force, with prune + on-disk fallback), `pruneWorktrees`, `hasBornHead`, `isWorkingTreeDirty`. Patch captured on **every** terminal path (success/cancel/budget/failure) BEFORE the worktree is removed; a startup sweep reaps orphans left by a hard kill.
- **Bounds & gates.** `--write` requires kimi-code **≥ 0.18.0** (the hard `KIMI_CODE_AGENT_SWARM_MAX_CONCURRENCY` cap — below it a write fan-out has no peak bound), a git repo with a committed HEAD (clean `WRITE_SWARM_NOT_A_REPO` / `WRITE_SWARM_NO_HEAD` refusals), and the PreToolUse hook (refuses without it). Default `--max-concurrency` is **1 for write** (serialize — disjoint-target partitioning is prompt-only) vs 4 for read. Bases on HEAD: a **loud warning** fires when the working tree is dirty (uncommitted work is not in the worktree). The coordinator prompt forbids git mutation and nested `AgentSwarm`.
- **Lineage:** reuses `command_type:"rescue"` (write-capable, like pursue), `agent_profile "<swarm-write>"`; `/kimi:status` / `/kimi:result` / `/kimi:cancel` work unchanged. The result report prepends a patch-handoff header pointing at the `.patch` file (`git apply <path>`).
- **Runtime:** `runtime/parsing.ts` (`--write` boolean), `runtime/commands/swarm.ts` (`runWriteSwarm`, `executeSwarmJob` gains a `writeMode` seam threading the worktree spawn cwd + trusted root, `SWARM_WRITE_DEFAULT_MAX_CONCURRENCY` = 1, capture/cleanup/sweep), `runtime/cli-client.ts` (`swarmWriteWorkspaceRoot` → env), `runtime/paths.ts` (`worktreesDir`), `runtime/types.ts` (`swarm-write` log label).
- **Tests:** `swarm.test.ts` (`--write` parse + composition, write concurrency default = 1, write prompt), `approval-policy.test.ts` (swarm-write allows AgentSwarm/read, confines to the TRUSTED env root not payload cwd, fail-closes on a missing root, forwards deny, denies `Agent`), new `git-worktree.test.ts` (real-repo create → edit → capture-an-applyable-patch incl. new files → remove, main tree untouched). `bun run check` green. ## 1.2.7 — 2026-06-19

**`/kimi:swarm`: split `--cap` into a soft total-count hint + a hard `--max-concurrency` ceiling.** A fast-follow surface correction to v1.2.6, which had overloaded a single `--cap N` to mean *both* a soft prompt-injected total-subagent-count hint *and* a hard concurrency ceiling (`KIMI_CODE_AGENT_SWARM_MAX_CONCURRENCY`). The two flags are independent: `--cap 20 --max-concurrency 4` means "aim for ≤20 total, never more than 4 running simultaneously".

- **Runtime:** `runtime/parsing.ts` adds `SwarmArgs.maxConcurrency` + a `--max-concurrency` case (sharing a `parsePositiveIntFlag` helper with `--cap`, so both apply the same `Number.isInteger && > 0` predicate upstream's `resolveSwarmMaxConcurrency` requires); `runtime/commands/swarm.ts` threads `--max-concurrency` (not `--cap`) into `CliClientOptions.swarmMaxConcurrency`. ### Critical fix — kimi-code 0.2.0 compatibility

- **Session id capture now reads `role:"meta", type:"session.resume_hint"` from stdout stream-json** (the new transport kimi-code 0.2.0 introduced in [PR #47](https://github.com/MoonshotAI/kimi-code/pull/47)). - **Session id format widened.** kimi-code 0.2.0 emits `session_<uuid>` instead of bare `<uuid>`. The cli-client stores the token verbatim and round-trips it via `kimi -r <token>` — we treat it as opaque. The stderr-fallback regex accepts both formats so 0.1.x users on text-output mode keep working alongside 0.2.0+ users on stream-json.
- **Stream-json parser learned `role:"meta"`.** Previously meta records were rejected as "unknown role" malformed. - **Stderr fallback regex tightened to anchored full-UUID.** Initial widening to accept `session_<uuid>` used the loose pattern `session_[0-9a-f-]{8,}`, which would have accepted `session_--------` (8 dashes) or any 8+ char hex-dash token. The "anchored full-UUID regex" safety invariant documented in `AGENTS.md` is preserved by requiring both alternations to match a full UUID payload — `session_<uuid>` and bare `<uuid>` are now symmetric. ## 1.0.0-alpha.3 — 2026-05-25

> **Roadmap to GA:** see [ROADMAP-TO-GA.md](./ROADMAP-TO-GA.md). The deferred items from the three audit rounds + production smoke testing are triaged into GA blockers (4), high-priority post-GA (3), and polish backlog (3). GA gate ≈ 1 working day of focused work.

### Fixed

- **Cancellation: grandchild orphan (CRITICAL, production-observed).** kimi-code 0.1.1's internal `LocalKaos` spawns every Bash tool subprocess with `detached: true` deliberately — so kimi-code can group-kill its own tools during cancellation. This gives bash subprocesses their own PGID (sibling to kimi-code's PGID, not nested). The alpha.2 process-group fix (`process.kill(-kimi_pid, ...)`) therefore only killed kimi-code itself; the bash grandchildren survived as orphans. Reproduced in production smoke testing — `/kimi:cancel` left `bun test` running indefinitely after the cancel completed.

  **Fix:** On POSIX, enumerate the descendant tree once at abort time (BFS over `/proc/*/status` on Linux, `ps -axo pid=,ppid=` snapshot on macOS, `pgrep -P` recursive as fallback; depth bounded at 8, pid count bounded at 512). The snapshot is reused for both SIGTERM and the SIGKILL escalation 1500ms later — re-enumerating at SIGKILL would miss any grandchildren whose parent (kimi) died from SIGTERM and reparented them to launchd, since the PPID-walk roots at kimi-code's now-dead pid. After per-pid kill, each descendant ALSO gets a negative-pid (process-group) kill as defense-in-depth, because each bash subprocess is itself a session leader and may have its own children that our enumeration missed (e.g. just-spawned pipeline kids). Win32 is unchanged — descendant reaping on Windows is a known limitation, documented in `runtime/cli-client.ts`.

  **Regression coverage:** New `tests/helpers/process-group-grandchild.ts` spawns its sleep grandchild with `{ detached: true }` to mirror kimi-code's actual production shape. New test in `tests/runtime/cli-client.test.ts` parses the grandchild PID via stdout, aborts the parent, waits for the SIGKILL escalation window, then asserts ESRCH on the grandchild. Confirmed to fail on the alpha.2 process-group-only path. Replaced an older sh-based test that could pass via shell SIGHUP cleanup semantics rather than actual descendant signaling.

  **Why this is a real safety regression rather than UX polish:** under `/kimi:rescue` an approved long-running tool (e.g. `bun test`, `cargo check`) kept consuming model tokens, file descriptors, and CPU after the user thought the job was cancelled. For build/test commands the workspace impact is bounded by the rescue allowlist's read-only-shape constraints, but the denial-of-cancellation is unacceptable for a write-capable surface. Surfaced by `/kimi:challenge` Finding 4 during smoke testing (challenge mode literally predicted this exact gap) and confirmed empirically.

### Investigation notes

- kimi-code 0.1.1's `detached: true` is a deliberate design choice in its `LocalKaos.exec` abstraction, paired with kimi-code-side `process.kill(-pid, ...)` cancellation. The behavior is structural and unlikely to change in the 0.1.x line. There is no env var or flag to disable it (confirmed by binary-strings inspection and source-level grep of the bundled Node binary at `~/.kimi-code/bin/kimi`).
- Production smoke testing observed a three-level PGID chain: plugin (own PGID from our `detached: true`) → kimi-code (own PGID from kimi-code's spawn shape) → bash (own PGID from kimi-code's `LocalKaos.exec`). All three are siblings, not nested. This is the shape the alpha.3 fix now handles.

### Pre-tag audit hardening

Two further multi-agent rounds (Claude code-reviewer + Codex codex-rescue, plus plugin-validator and claude-code-guide for spec compliance) found these classes during the pre-tag audit. All closed before tag:

- **rescue.ts skipped the hook-path drift gate** — the optional `expectedHookPath` parameter let a stale managed block silently re-enable kimi-code's auto-approve. Verifier is now strict-by-default and always reconstructs the canonical command via the shared `runtime/hooks/install-paths.ts` module.

- **Relative `KIMI_PLUGIN_CC_HOOK_SCRIPT` override** — kimi-code spawns hooks via `/bin/sh -c` with a cwd that may differ from the companion's. Override is now required to be absolute, matching the `KIMI_PLUGIN_CC_NODE_BIN` contract.

### Round 3 audit hardening

A third multi-agent audit pass (Claude code-reviewer + Codex + plugin-validator + claude-code-guide) found one High, four Medium, two Low, and several polish gaps. All closed before tag:

- **Process-group cancellation (HIGH)** — `runtime/cli-client.ts` spawned kimi-code with default process-group behavior, so `child.kill(SIGTERM/SIGKILL)` only hit the immediate process. kimi-code's Bash tool subprocesses ran as grandchildren and survived cancel — a denial-of-cancellation issue where long-running approved subprocesses kept consuming workspace state after the plugin reported cancellation. POSIX now spawns with `detached: true` (own process group) and signals the negative pid (`process.kill(-child.pid, ...)`). ESRCH/EPERM fall through to direct `child.kill()`. win32 keeps the original direct-kill path (negative-pid signaling does not exist there; grandchild reaping on Windows is a known gap).
- **Session-id capture: incremental + anchored (MEDIUM)** — `runtime/cli-client.ts` only parsed the session id from the final 8192-char `stderrTail` on close; if kimi-code emitted the announce line early and then wrote more than 8192 bytes of stderr, the id was evicted and resume/replay handles silently disappeared. `runtime/stream-json.ts` regex was unanchored and accepted any `[0-9a-f-]{8,}` token, so a hostile Bash command under `/kimi:rescue` could `echo 'To resume this session: kimi -r <fake>' >&2` and poison the captured id. Capture now runs in the stderr `data` handler (first announce wins, pinned), regex tightened to anchored line-bounded full-UUID shape (`/^To resume this session:\s+kimi\s+-r\s+([0-9a-f]{8}-[0-9a-f]{4}-[0-9a-f]{4}-[0-9a-f]{4}-[0-9a-f]{12})\s*$/im`), and `stderrTail` scan remains as a fallback.
- **Stream-json line size cap (MEDIUM)** — `StreamJsonParser.push()` appended every chunk into one in-progress buffer until `\n` appeared, with no upper bound; a single 1MB+ unterminated stdout line could land whole in `malformed[]` and the diagnostics log. New `MAX_STREAM_JSON_LINE_BYTES = 1_048_576` guard emits a malformed outcome with a truncated preview, clears the buffer, and continues parsing. `cli-client.ts` also truncates `entry.line` before storing for diagnostics.
- **Drift gate untracked-file gap (MEDIUM, convergent with code-reviewer)** — `bun run check`'s `git diff --exit-code -- dist` caught modifications but not untracked files. A new `runtime/foo.ts` whose compiled `dist/foo.js` was forgotten by `git add` would silently pass the gate. The check now additionally fails when `git ls-files --others --exclude-standard -- dist` is non-empty, and prints the offending files so the developer knows what to stage.
- **`buildManagedBlock` env divergence** — the installer's managed-block writer called `buildHookShellCommand(hookScriptPath, process.env)` while the verifier and `--check` path resolved the canonical command from a parameter `env`. Production masked this (context.env === process.env), but any future caller or test that passed divergent env would produce an unfixable "installed: false" loop. `buildManagedBlock` now takes `env: NodeJS.ProcessEnv` and the install path threads `context.env` through — single source of truth for the canonical command bytes stays in `runtime/hooks/install-paths.ts`.
- **Agent color collision** — `kimi-review`, `kimi-challenge`, and `kimi-ask` all declared `color: cyan`, defeating Claude Code's per-agent UI hint. `kimi-challenge` moved to `yellow` (adversarial framing → warning color); the read-only narrative trio (`kimi-review`, `kimi-ask`) keep cyan and `kimi-rescue` keeps magenta as the only write-capable surface.
- **Missing `argument-hint` on lifecycle commands** — `replay`, `result`, `status`, `cancel` accepted positional or flag arguments but exposed no hint in the slash-command palette.
